# ゼミ質疑支援アプリ 要件定義書

版：0.4 ／ 2026-09-16 ／ 想定開発時間：5時間程度（半日ハッカソン）

0.3 からの変更点：FR-13 を「記録の出力」に組み替え，Teams 投稿を任意の配送手段とした．
Teams チャネルの作成権限が無くても記録が残るようにするためである（§9）．
学年の選択肢に D2／D3 を追加した．

0.2 からの変更点：着手前の確認で見つかった仕様の穴5件を解消した．
セッションの起動時自動生成（FR-01，§5），発表中の質問本文の非配信（FR-06），
わからん率の分母の定義（FR-11），消化の取り消し，QR画像のエンドポイント．
あわせて §14 の未決事項から「セッションの作成者」を解消した．
詳細は `docs/protocol.md` 0.3 を参照．

0.1 からの変更点：技術構成を確定（§10），テスト方針を追加（§11），役割分担を追加（§3.2）．

## 1. 背景と目的

研究室の中間発表・期末発表のレビューでは，発表後に学生と指導教員が質疑を行う．
しかし学生が挙手して質問することの心理的な障壁が高く，実際には教員のみが質問して終わる場面が多い．
また，発表のどの部分で聴衆の理解が途切れたかは，発表者にも指導教員にも見えていない．

本アプリは，聴衆が発表中にスマートフォンから匿名で質問を投稿し，
質疑の場でそれを共感数順に消化する仕組みを提供する．
あわせて，聴衆が理解を見失った時刻を記録し，発表全体を通した理解度の推移として可視化する．

目的は次の2点である．

1. 学生からの質問数を増やし，質疑を教員以外にも開くこと
2. 発表者が「どこで伝わらなかったか」を客観的な記録として受け取ること

## 2. スコープ

### 2.1 本版で実現すること

- 発表中の匿名質問投稿と「わからん」記録
- 質疑時の質問一覧表示，共感による並び替え，消化管理
- わからん率の時系列グラフ表示
- 質疑終了時の記録の出力（画面からのコピー．設定があれば Teams へも投稿）
- 1回のゼミにおける複数発表の連続進行

### 2.2 本版では実現しないこと

- ユーザ認証，アカウント管理（学年の選択のみで参加する）
- 過去の発表の履歴閲覧画面（記録は Teams 投稿に残す）
- スライドとの連動（わからんの時刻はスライド番号ではなく経過時間で記録する）
- 投稿内容の事後編集・削除，不適切投稿の管理

## 3. 利用者と役割

### 3.1 アプリの利用者

| 区分 | 人数の目安 | 使用端末 | 行うこと |
|---|---|---|---|
| 発表者 | 1回あたり3〜5名（交代） | 自身のノートPC | 発表の開始・終了操作，質疑の進行 |
| 学生 | 10〜20名 | 各自のスマートフォン | わからん送信，質問投稿，共感 |
| 指導教員 | 1〜2名 | スマートフォンまたはPC | 学生と同じ操作 |

### 3.2 開発時の役割分担

- **Claude Code**：実装のほぼ全て
- **人間（渡嘉敷）**：実機での動作確認，見た目の判断，軌道修正

人間は React / TypeScript に不慣れである．C#/WPF，Python，Java の経験があるため
Python コードは読める．この分担が §10 の技術構成を規定している．

## 4. 利用の流れ

1. サーバを起動する．ゼミ回（セッション）は起動時に自動生成される．スクリーンにQRコードを投影する
2. 参加者がQRを読み，学年（B3／B4／M1／M2／D1／D2／D3／教員）を選んで参加する．操作はゼミ開始時の1回のみ
3. 発表者が自身のPCで発表者ビューを開き，「発表開始」を押す
4. 発表中，参加者は「わからん」と質問を送信する．スクリーンにはスライドのみを映す
5. 発表者が「発表終了」を押すと，参加者の画面が自動で質疑モードに切り替わる
6. 発表者がスクリーンを質疑ビューに切り替え，共感数順に質問を消化する
7. 「質疑終了」で記録が出力され，次の発表者が「発表開始」を押して交代する

## 5. 画面一覧

| 画面 | パス | 表示端末 | 主な要素 |
|---|---|---|---|
| 参加 | `/join` | スマホ | 学年選択 |
| 発表中 | `/live` | スマホ | わからんボタン，質問入力，自分の投稿一覧 |
| 質疑中 | `/live` | スマホ | 質問一覧，共感ボタン，追加質問入力 |
| 発表者 | `/present` | 発表者PC | QR，接続人数，質問件数，開始／終了操作 |
| 質疑 | `/review` | スクリーン | わからんグラフ，質問リスト，消化操作 |

スマホ側の2画面は同一URLとし，発表の状態に応じてサーバから切り替えを配信する．
参加者に画面遷移を意識させない．

**セッションを作成する画面は設けない．** セッションはサーバ起動時に1つだけ自動生成する．
発表（発表者名・タイトル）の登録は `/present` の上部で発表者自身が行う．
進行役を置かず，発表者が交代のたびに自分で登録して開始する運用とする．

## 6. 機能要件

優先度：**Must**（無ければ成立しない）／**Should**（デモの価値を決める）／**Could**（余力があれば）

| ID | 機能 | 内容 | 優先度 |
|---|---|---|---|
| FR-01 | セッション作成 | サーバ起動時にゼミ回を1つ自動生成し，参加用URLとQRを発行する．QRは `GET /api/sessions/{sid}/qr.png` で配信し，URLのホスト名はリクエストの `Host` ヘッダから組む | Must |
| FR-02 | 参加と学年登録 | 学年を1つ選んで参加する．選択はブラウザに保持し，再読込でも維持する | Must |
| FR-03 | 発表の開始・終了 | 発表者が操作する．開始時に未完了の発表があれば自動的に終了させ，進行中の発表が2つ以上存在しないようにする | Must |
| FR-04 | 状態の一斉配信 | 発表の状態変化を全接続端末へ即時に配信し，スマホ画面を自動で切り替える | Must |
| FR-05 | 質問投稿 | 本文（200字以内）と学年を記録する．投稿者名は記録しない | Must |
| FR-06 | 質問の非開示 | 発表中は質問の本文を発表者ビューに表示せず，件数のみ表示する．参加者の端末へも本文を配信せず，各自の投稿のみを手元に保持する | Must |
| FR-07 | 質問一覧 | 質疑モードで全参加者と質疑ビューに質問を一覧表示する | Must |
| FR-08 | 共感と並び替え | 1参加者につき1質問1回まで．共感数の降順，同数なら投稿の早い順に並べる | Should |
| FR-09 | 消化管理 | 質疑ビューで質問を「消化済」にでき，一覧の末尾へ移動させる．投影中の誤操作に備え，消化は取り消せること | Should |
| FR-10 | わからん記録 | 押下時の発表開始からの経過秒を記録する．同一参加者は30秒に1回まで受け付ける | Must |
| FR-11 | わからんグラフ | 30秒刻みで集計し，割合の折れ線として表示する．最大値の区間を強調する．分母はその発表中に一度でも接続した人数とし，画面に出す「接続中」の人数とは区別する | Should |
| FR-12 | 学年の丸め | その発表で投稿者が1名のみの学年は，表示を「学生」に丸める | Should |
| FR-13 | 記録の出力 | 質疑終了時に，発表1件分の記録を Markdown で生成し，質疑ビューからコピーできるようにする．`TEAMS_WEBHOOK_URL` が設定されていれば，同じ内容を Adaptive Card で Teams へも投稿する | Should |
| FR-14 | 回答メモ | 発表者が後日，質問ごとに回答を記入できる．記録に入力用リンクを含める | Could |
| FR-15 | データ永続化 | 保存先を用意し，サーバ再起動後もデータを保持する | Could |

**FR-14 と FR-15 は一体で扱う．**
回答メモを後日入力する要件が無ければ永続化も不要となり，メモリ保持で足りる．
時間が不足した場合はこの2つを同時に外し，FR-13 の記録を代替とする．
本版は外す前提で計画しており，実装順序にも含めていない．

## 7. データモデル

| エンティティ | 主な属性 | 関係 |
|---|---|---|
| Session | id, title, date | ゼミ1回．Presentation を複数持つ |
| Presentation | id, session_id, presenter, title, state（waiting／live／review／closed）, started_at, ended_at | Question と Confusion を複数持つ |
| Participant | id, session_id, grade, token | Session に属する |
| Question | id, presentation_id, participant_id, grade, body, created_at, resolved | Empathy を複数持つ |
| Empathy | question_id, participant_id | (question_id, participant_id) で一意 |
| Confusion | id, presentation_id, participant_id, elapsed_sec | — |

参加者の同一性は，参加時に発行したランダムなトークンをブラウザに保存して判定する．
氏名・学籍番号・IPアドレスは一切保持しない．

Presentation は上記に加え，**その発表中に一度でもWS接続したトークンの集合**を保持する．
FR-11 の分母に用いる．発表開始時にクリアする．

## 8. 非機能要件

- **同時接続数**：25台を上限とする．研究室規模を超える負荷は想定しない
- **応答性**：投稿から全端末への反映まで1秒以内
- **ネットワーク**：学内LAN内で完結する．外部からの接続は想定しない
- **オフライン動作**：CDN やオンラインフォントに依存しない．外部への通信は Teams 投稿のみ
- **可用性**：ゼミ1回（最大2時間）の間，サーバが継続動作すること
- **匿名性**：投稿と参加者トークンの紐付けはサーバ内部に留め，いかなるレスポンスにも含めない
- **対応ブラウザ**：iOS Safari 18以降，Android Chrome 111以降．発表者PCは Chrome を使用する
- **アクセシビリティ**：`prefers-reduced-motion: reduce` を尊重する

## 9. 記録の出力と外部連携

**記録の生成と配送を分離する．** 開発者はチャネルを作成する権限を持たず，
Teams への投稿が最後まで実現できない可能性がある．
配送手段に依存した設計にすると，その場合に記録が何も残らない．

### 9.1 画面への表示（既定．常に行う）

質疑終了時に記録を Markdown で生成し，質疑ビューの「記録をコピー」ボタンで
クリップボードへ写す．発表者が任意の場所（Teams のチャット，OneNote 等）へ自分で貼る．
外部への通信も，Teams 上の権限も要らない．これを本版の既定とする．

### 9.2 Teams への投稿（任意）

環境変数 `TEAMS_WEBHOOK_URL` が設定されている場合に限り，同じ内容を投稿する．
未設定なら投稿を試みない．失敗してもアプリの動作を止めない．

従来の Office 365 コネクタは 2026年5月に廃止されているため，
Power Automate Workflows の Webhook を使用する．
Teams のチャネルから「Send webhook alerts to a channel」テンプレートでフローを作成し，
発行された URL へ POST する．ペイロードは MessageCard ではなく **Adaptive Card 形式**である必要がある．

**チャネルの新設は必要ない．** 既存チャネルの「⋯ → ワークフロー」から
フローを作成できるかをまず確認する．チャネルを作る権限と，
既存チャネルにワークフローを追加する権限は別である．

投稿内容は §`docs/protocol.md` に定義する．
これが最後まで通らなくても 9.1 で記録は残るため，**着手を妨げない．**

## 10. 技術構成

| 層 | 採用 |
|---|---|
| サーバ | Python 3.11+ / FastAPI |
| 配信 | WebSocket（サーバ→クライアントの一方向） |
| データ | プロセス内メモリ（dataclass + dict） |
| フロント | 素の HTML / CSS / JavaScript（ビルドツール不使用） |
| 並び替え演出 | View Transitions API |
| グラフ | SVG を直接生成 |

### 10.1 フロントエンドフレームワークを採用しない理由

当初 React + Motion を検討した．並び替えアニメーションを素の JavaScript で書くと
FLIP を自前実装することになり，30分から1時間を要するためである．

しかし View Transitions API の同一ドキュメント内遷移が
Chrome 111以降，Firefox 144以降，Safari 18以降で利用可能となり（2025年10月に Baseline）， 
`document.startViewTransition()` と `view-transition-name` の指定のみで
同等の演出が実質5行で得られる．Motion を導入するためだけに React を採用する理由が無くなった．

加えて，実装を Claude Code が担い，人間が確認と軌道修正を行う体制では，
律速するのは実装速度ではなく**確認と修正の往復速度**である．
ビルド待ちが無く，依存関係が壊れず，壊れたら丸ごと書き直せる構成が，この体制に最も適合する．

### 10.2 デスクトップアプリを採用しない理由

参加者のスマートフォンからの接続が必須であること，
および発表者や教員のPCに何もインストールさせずに使えることによる．

## 11. テスト方針

**一人ではテストできない機能がある．** 共感による並び替えも，わからん率のグラフも，
複数人が同時に触らないと動作を確認できない．スマートフォン1台では
質問1件・共感1票の状態しか作れず，レイアウトの破綻も発見できない．

このため `tools/fake_audience.py` を実装順序の早い段階で用意する．
12人分の接続を張り，ランダムな間隔で質問投稿とわからん送信を流す検証用スクリプトである．
これにより常に本番相当の画面を見ながら確認と軌道修正ができる．

### 確認ポイント

| 経過 | 状態 | 人間が判断すること |
|---|---|---|
| 1時間 | スマホから接続でき，わからんが送れる | 接続できるか |
| 2時間 | 質問が溜まり，質疑ビューに一覧が出る | 流れとして成立するか |
| 3時間 | 共感で並び替わり，アニメーションが付く | 気持ちよさ．**ここで見た目の方向性を確定する** |
| 4時間 | グラフと配色が入った完成形 | プロジェクタに投影して読めるか |

3時間地点と4時間地点は，必ず実際のスクリーンに投影して判断する．
手元のディスプレイのみの確認では，当日ほぼ確実に文字サイズを外す．

## 13. リスク

| リスク | 影響 | 対応 |
|---|---|---|
| 学内Wi-Fiのクライアント間通信が遮断されている | 致命的．スマホからサーバへ一切届かない | 開発開始前に確認する．駄目ならテザリング，またはトンネリングで外部URLを発行する |
| Teams への投稿ができない（チャネル作成権限が無い，Power Automate が制限されている） | 記録の配送手段が失われる | 記録の生成と配送を分離し，画面からのコピーを既定とする（§9.1）．Teams は任意の追加とする |
| 学年表示から投稿者が特定される | 匿名性が実質的に失われ，質問が出なくなる | FR-12 の丸め処理を必ず入れる |
| 教員の質問に共感が集まらず下位に沈む | 時間切れで消化されない | 学年バッジ「教員」で識別できるようにし，発表者の判断で拾う運用とする |
| 誹謗中傷に近い投稿が出る | ゼミの場が荒れる | 本版では機能で防がない．運用上のルールとして事前に周知する |
| 投影時に文字が読めない | デモとして成立しない | 3時間地点と4時間地点で実際に投影して確認する |

## 14. 未決事項

- **サーバの設置場所**：発表者が各自のPCで交代する以上，サーバは固定の端末に置く必要がある．研究室の常設PCか，進行役のPCか．IPアドレスが変動しても，QRを `Host` ヘッダから組むため周知の手順は不要である（毎回QRを読み直させる）
- **投稿先の Teams チャネル**：チャネルを作成する権限が無い．既存チャネルへのワークフロー追加が可能かを確認する．不可なら §9.1 のみで運用する（実装は妨げられない）

学年の選択肢は B3／B4／M1／M2／D1／D2／D3／教員で確定した．
D2・D3 に現在の在籍者はいないが，来年度以降のために含める．研究生・留学生は在籍しないため含めない．
